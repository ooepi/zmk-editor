# Implementation plan — Milestones 1–2

Spec: [docs/specs/2026-09-26-zmk-editor-design.md](../specs/2026-09-26-zmk-editor-design.md)

## Milestone 1 — scaffold

1. `package.json` with Vite 8, React 19, TypeScript 6 (strict, `noUncheckedIndexedAccess`), ESLint 10 flat config with typescript-eslint and react-hooks, Vitest 5.
   TypeScript stays on 6.0.x because typescript-eslint doesn't support 7 yet.
2. Scripts: `dev`, `build` (`tsc -b && vite build`), `typecheck`, `lint`, `test`, `test:watch`, `preview`.
3. `vite.config.ts`: relative `base` so the build works under `https://<user>.github.io/zmk-editor/`. Vitest config lives in the same file.
4. A minimal app shell in `src/ui/`: header, theme toggle (dark by default, light too, stored in localStorage), placeholder for the keyboard canvas. Colors are CSS custom properties so Milestone 3 builds on them.
5. `.github/workflows/ci.yml`: lint, typecheck, test and build on every push and PR.
   `.github/workflows/pages.yml`: build and deploy to GitHub Pages on pushes to `main`.
6. An ESLint rule blocks `react` imports inside `src/core/`.

Done when `npm run lint && npm run typecheck && npm test && npm run build` all pass locally and in CI.

## Milestone 2 — core model, generator, importer

All code in `src/core/`, no React. Every step is test-first.

### Data model (`src/core/model.ts`)

- `Binding` = `{ behavior, params: string[] }`. Params stay as source tokens (`LG(PG_UP)`, `BT_SEL 0`, a `#define` name), so symbolic names survive a round trip.
- `KeymapModel`:
  - `topLevel`: ordered `#include` / `#define` / other directives, `&node { … }` overrides and raw text the parser couldn't model. Order is kept because defines often must precede includes.
  - `behaviors`: one shape for every behavior: `name`, `label`, `compatible`, `bindings`, other `properties` in source order. The kind (hold-tap, mod-morph, macro, sensor-rotate, tap-dance, other) comes from `compatible`, so unknown behaviors round-trip too. Macros are generated into a `macros` node, the rest into `behaviors`.
  - `combos`: `name`, `keyPositions` and `layers` as tokens, `binding`, other `properties`.
  - `layers`: `name`, `displayName`, `bindings`, `sensorBindings`, other `properties`.
  - `extraNodes`: children of `/` that aren't modeled (e.g. `conditional_layers` until v2), kept as generic devicetree nodes.
- `KconfigModel`: lines (`set`, `comment`, `blank`), so commented-out options survive.
- `WestModel`: `zmkVersion` plus `modules` (`name`, `remote`, `urlBase`, optional `revision` override, optional `import`). A module without a `revision` follows `zmkVersion`.
- `BuildModel`: the `include` matrix (`board`, `shield`, `snippet`, `cmakeArgs`, `artifactName`).
- `ZmkConfig`: `keyboard` (shield base name), `keymap`, `kconfig`, `west`, `build`.

### Devicetree layer (`src/core/dts/`)

1. `stripComments` — replaces comments with spaces, keeps offsets and newlines, respects strings.
2. `parseDts` — top-level items (directives, `/ { }` roots merged, `&ref { }` overrides, macro invocations and anything else as raw text). A parse error inside one item turns that item into raw text instead of failing the file.
3. `tokenizeCells` — splits `< … >` content, keeping parenthesised expressions whole.
4. `printNode` — generic, deterministic devicetree printer.

### Keymap (`src/core/keymap/`)

1. `importKeymap(text)` → `{ model, warnings }`.
2. `generateKeymap(model, layout?)` → text. Layer bindings are column-aligned on the layout's text grid; each layer gets an ASCII comment with key labels. Without a layout, bindings wrap at 12 per row.
3. `src/core/layouts/lily58.ts` — the Lily58 text grid (58 keys).

### Other files (`src/core/files/`)

1. Kconfig parse/generate.
2. `west.yml` parse/generate (`yaml` package for parsing, hand-written output for stable formatting). `findVersionMismatches` lists modules pinned to another ref.
3. `build.yaml` parse/generate (accepts top-level `board`/`shield` arrays and `include`).
4. `generateWorkflow(zmkVersion)` — `build-user-config.yml@<zmkVersion>`, so the workflow and `west.yml` can't disagree.
5. `importConfig(files)` / `generateConfig(config)` over the repo paths `config/<keyboard>.keymap`, `config/<keyboard>.conf`, `config/west.yml`, `build.yaml`, `.github/workflows/build.yml`.

### Tests

- Unit tests per module.
- Fixture tests on `test/fixtures/lily58/`:
  - the model has 6 layers × 58 bindings, 2 sensor-rotate behaviors, 2 overrides, and the expected sensor bindings;
  - import → generate → import gives an equal model, and generating twice gives identical text;
  - west/build/kconfig round-trip the same way;
  - the generated workflow and `west.yml` use the same ZMK version.

Known limits (accepted for now): comments inside the keymap aren't kept (the layer comments are regenerated); zmk-helpers macros such as `ZMK_COMBO(...)` are kept as raw text rather than modeled.
